History: R28b (alpha8) cut the glide start from 5 dp to 2.5 dp and fixed the padding and the second-thumb hand-over. The owner reported the stray letter again, so the threshold was not the cause. Reading every place where a letter can be typed while a finger is down on a letter key

## 2. R34e - "if i have translation feature on, then switch apps or tabs, automatically turn translation off" (done, tests)

Before: the toggle stayed on across every box and app (only a 10-minute idle timer could switch it off). Now translating belongs to ONE text box (`KeyboardPresenter.translateBox`: the app, the field id, the kind of box = input class + variation, the hint, label, field name and private options; NOT the action key or capital flags, which apps change while typing). It is switched off, and the strip says so once (`translate_auto_off`), when
* Android starts a NEW input session (`onStartInputView(restarting = false)`: another app, another window, Recents, a lock screen, a rotation);
* the app restarts input for a DIFFERENT box (another field of the same app, a browser tab that describes its box differently, the next box of a form);
* the keyboard goes away (`onFinishInputView` / `onWindowHidden`: Back, the screen turning off, the browser's tab switcher); coming back to the same box does not bring it back on.
It stays on while the same box keeps the keyboard, including after Send / a restart with the same box. Tests: `KeyboardPresenterTest` (7, `translating...`), `KeysServiceTest.translatingStaysOnInTheSameBoxButSwitchesOffWhenTheKeyboardLeavesOrAnotherAppComes` (the service passes `restarting` and the hide events through), the two R24c tests were updated (a login box is a new box now). Honest limit: a browser that swaps tabs WITHOUT hiding the keyboard and describing the box identically cannot be told apart from the same box; the keyboard hiding (the usual case when a tab is switched) catches it.

## 3. R34b / R34c - e-mail boxes (done, tests)

Why "it still isn't recognizing email fields and suggesting my email addresses" (R32c shipped the feature in alpha11). Three real causes found by reading the code, one more for day one:
1. **A typed address was thrown away when the focus moved to the next box of the same window.** Android calls `onFinishInput` only when the whole input session ends; a login page (e-mail box, then the password box) is ONE session, the next box arrives as `onStartInputView(restarting = true)`, and `startInput` called `emailLearner.reset()` which dropped the address that was waiting to be learned. So the commonest way an address is typed (then tap the password box) never taught the keyboard anything. Fix: the old box is finished (`emailLearner.finishField()`) before the new one starts. Test `anAddressTypedInTheLoginBoxIsLearnedWhenTheFocusMovesOnWithoutTheBoxBeingFinished` is red without the fix.
2. **Learning and the strip only worked in boxes the app flagged as e-mail boxes** (`inputType` e-mail address variation); an address typed in an ordinary box was learned only when a space/comma/Enter followed it. Now every ordinary box (text, search, e-mail; never password, address bar, number, phone, or where the app asked for private typing) remembers the address at the end of the text after each key (`EmailLearner.afterKey`, gated by the allocation-free `InputController.atSignNear()`) and learns it when the box is left.
3. **Recognition**: login pages and apps often make the e-mail box a plain text box. `FieldInfos.looksLikeEmailBox` reads the hint, label and field name ("Email", "E-mail address", "Username or email", "Correo electrónico", `user_email` ...; never "Email subject", "Search mail", "Message body", "Email notifications"; single-line plain or web text boxes only, never password / search / address-bar / subject boxes): such a box is an e-mail box (the `@` and `.com` keys, no capitals, no composing text, the saved addresses on the strip). Chrome and WebViews send `type=email` as an e-mail inputType already (unchanged).
4. **Day one**: a new install knows no address. Settings > Learning > "My e-mail addresses" (new `EmailsActivity`): type an address, tap Add, it leads the strip from then on (stored as three uses so it is not the first to go); Remove per address.

R34c: once "name@" is typed, `EmailBook.suggest` offers domains: the ones this person's own addresses use (most used first), then `EmailBook.POPULAR_DOMAINS` (outlook.com, gmail.com, proton.me, hotmail.com, yahoo.com, icloud.com, protonmail.com, live.com, aol.com, msn.com: the owner's three first), filtered by what is typed of the domain ("tj@pro" -> proton.me, protonmail.com); the part before the @ keeps its capitals; a finished address is not offered again. The strip shows the domain only (a chip says "outlook.com", a tap puts in "tj@outlook.com", replacing what was typed of the address, no space after it; the picked address is remembered). It works in e-mail boxes AND in any ordinary text/search box once an @ stands inside the word being typed (not for "@bob" mentions). Switch: the existing Settings > "E-mail addresses". Tests: `EmailBookTest` 17, `EmailLearnerTest` 14, `AtSignNearTest` 2, `FieldInfosTest`, `KeyboardPresenterTest` (9 e-mail tests), `EmailsActivityTest` 2. NOT run on a device.
