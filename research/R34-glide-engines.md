## 1. R34d - "make the delay from first key to glide instant so it doesn't erroneously type one letter" (done, tests red -> green)

History: R28b (alpha8) cut the glide start from 5 dp to 2.5 dp and fixed the padding and the second-thumb hand-over. The owner reported the stray letter again, so the threshold was not the cause. Reading every place where a letter can be typed while a finger is down on a letter key
(`KeysView.pressDown / pressMove / pressUp / ACTION_POINTER_DOWN`) found three paths that type the FIRST key's letter although a glide is meant. All three sit in the window between "finger down" and "finger has moved 2.5 dp" (the owner's "delay from first key to glide"):

| # | what happened | why | fix (all in `KeysView`) | test (RED on alpha12, green now) |
| :- | :- | :- | :- | :- |
| 1 | A quick flick whose only touch events were DOWN and UP (a panel that sends no MOVE in between, or a flick faster than one sample) typed the letter the finger went down on, although the lift point was far away. | `pressUp` decided "tap" for any touch that was not yet `gliding`, without looking at where the finger lifted. | at the lift: a touch that has moved more than the glide start distance is a glide (`armed && movedFar(x, y)`), then the usual tap-or-glide decision at the end of the stroke. | `aFlickWhoseOnlyEventsAreTheTouchDownAndTheLiftIsAGlideNotTheFirstLetter` |
| 2 | A second finger that touched the screen in that window (a thumb that holds the tablet, a palm, a ghost touch of a cheap panel, the other thumb of two-thumb typing) TYPED the first finger's letter at once and switched tracking to itself, so the glide the first finger was about to draw was lost and a stray letter stayed. | `ACTION_POINTER_DOWN` while `armed` but not yet `gliding` called `finishHeldLetter()`. | The new finger is only recorded while the first finger may still glide (as R28b already did once a glide was running). The first finger carries on. If the NEW finger moves first it is the glide and the first one was a tap (typed then). If the first finger lifts without moving it is a tap and the recorded finger carries on as a new touch. A fast two-thumb overlap is far under 300 ms. | `aThumbThatHoldsTheTabletOnALetterTypesNothingWhenTheOtherFingerGlides`, `aThumbThatHoldsTheTabletAndAnotherThatTapsTypeOnlyTheTap` |

Not changed on purpose: the 2.5 dp start (tremor over it still ends as a tap at the lift: `stayedOnKey`), the strip/padding rules, rollover typing with glide off (a second finger still types the first letter at once there).
Honest limit: nothing here shows which of the three the owner's tablet hits; each is a real path found by reading the code and reproduced by a test. `Diagnostics` counts how often a resting finger was let go (the existing "a resting second finger was ignored N times" line), so the next report says if path 3 happens.

**Second half (found while reading `endGlide` / `stayedOnKey` again, same owner words): two limits grew with the size of the keys.** A touch counted as a TAP (typing the letter it began on) when it never left its key plus `TAP_MARGIN_PITCH` = 0.22 key widths, or when the whole stroke was shorter than `MIN_GLIDE_PITCHES` = 0.45 key widths. On phone keys (35 dp) that is 7.7 dp and 16 dp, about the size of a thumb's roll. On the owner's tablet it is 12 dp / 25 dp in portrait and **20 dp / 41 dp in landscape (key width 91 dp)**: a flick of 4 mm that ends in the neighbouring key's half typed the letter it began on ("as", "it", "no" ... drawn short). A thumb rolls the same few dp on every keyboard (Android's own tap slop is 8 dp), so both limits are now capped in dp (`TAP_MARGIN_MAX_DP` = 8, `MIN_GLIDE_MAX_DP` = 16); on phone-sized keys the key-width figure is the smaller one and nothing changes (test `onPhoneSizedKeysTheLimitsAreExactlyAsBefore`). `aShortFlickToTheNextKeyOnBigKeysIsAGlideNotTheLetterItBeganOn` is red before the cap, `aThumbThatRollsAFewDpOnBigKeysIsStillATapAndAnEdgeTapToo` guards the other side (KeysViewTest 70 green). Not run on a device; shipped in alpha15.

## 2. R34e - "if i have translation feature on, then switch apps or tabs, automatically turn translation off" (done, tests)

Before: the toggle stayed on across every box and app (only a 10-minute idle timer could switch it off). Now translating belongs to ONE text box (`KeyboardPresenter.translateBox`: the app, the field id, the kind of box = input class + variation, the hint, label, field name and private options; NOT the action key or capital flags, which apps change while typing). It is switched off, and the strip says so once (`translate_auto_off`), when
* Android starts a NEW input session (`onStartInputView(restarting = false)`: another app, another window, Recents, a lock screen, a rotation);
* the app restarts input for a DIFFERENT box (another field of the same app, a browser tab that describes its box differently, the next box of a form);
* the keyboard goes away (`onFinishInputView` / `onWindowHidden`: Back, the screen turning off, the browser's tab switcher); coming back to the same box does not bring it back on.
It stays on while the same box keeps the keyboard, including after Send / a restart with the same box. Tests: `KeyboardPresenterTest` (7, `translating...`), `KeysServiceTest.translatingStaysOnInTheSameBoxButSwitchesOffWhenTheKeyboardLeavesOrAnotherAppComes` (the service passes `restarting` and the hide events through), the two R24c tests were updated (a login box is a new box now). Honest limit: a browser that swaps tabs WITHOUT hiding the keyboard and describing the box identically cannot be told apart from the same box; the keyboard hiding (the usual case when a tab is switched) catches it.

## 3. R34b / R34c - e-mail boxes (done, tests)

Why "it still isn't recognizing email fields and suggesting my email addresses" (R32c shipped the feature in alpha11). Three real causes found by reading the code, one more for day one:
1. **A typed address was thrown away when the focus moved to the next box of the same window.** Android calls `onFinishInput` only when the whole input session ends; a login page (e-mail box, then the password box) is ONE session, the next box arrives as `onStartInputView(restarting = true)`, and `startInput` called `emailLearner.reset()` which dropped the address that was waiting to be learned. So the commonest way an address is typed (then tap the password box) never taught the keyboard anything. Fix: the old box is finished (`emailLearner.finishField()`) before the new one starts. Test `anAddressTypedInTheLoginBoxIsLearnedWhenTheFocusMovesOnWithoutTheBoxBeingFinished` is red without the fix.
2. **Learning and the strip only worked in boxes the app flagged as e-mail boxes** (`inputType` e-mail address variation); an address typed in an ordinary box was learned only when a space/comma/Enter followed it. Now every ordinary box (text, search, e-mail; never password, address bar, number, phone, or where the app asked for private typing) remembers the address at the end of the text after each key (`EmailLearner.afterKey`, gated by the allocation-free `InputController.atSignNear()`) and learns it when the box is left.
3. **Recognition**: login pages and apps often make the e-mail box a plain text box. `FieldInfos.looksLikeEmailBox` reads the hint, label and field name ("Email", "E-mail address", "Username or email", "Correo electrónico", `user_email` ...; never "Email subject", "Search mail", "Message body", "Email notifications"; single-line plain or web text boxes only, never password / search / address-bar / subject boxes): such a box is an e-mail box (the `@` and `.com` keys, no capitals, no composing text, the saved addresses on the strip). Chrome and WebViews send `type=email` as an e-mail inputType already (unchanged).
4. **Day one**: a new install knows no address. Settings > Learning > "My e-mail addresses" (new `EmailsActivity`): type an address, tap Add, it leads the strip from then on (stored as three uses so it is not the first to go); Remove per address.

R34c: once "name@" is typed, `EmailBook.suggest` offers domains: the ones this person's own addresses use (most used first), then `EmailBook.POPULAR_DOMAINS` (outlook.com, gmail.com, proton.me, hotmail.com, yahoo.com, icloud.com, protonmail.com, live.com, aol.com, msn.com: the owner's three first), filtered by what is typed of the domain ("tj@pro" -> proton.me, protonmail.com); the part before the @ keeps its capitals; a finished address is not offered again. The strip shows the domain only (a chip says "outlook.com", a tap puts in "tj@outlook.com", replacing what was typed of the address, no space after it; the picked address is remembered). It works in e-mail boxes AND in any ordinary text/search box once an @ stands inside the word being typed (not for "@bob" mentions). Switch: the existing Settings > "E-mail addresses". Tests: `EmailBookTest` 17, `EmailLearnerTest` 14, `AtSignNearTest` 2, `FieldInfosTest`, `KeyboardPresenterTest` (9 e-mail tests), `EmailsActivityTest` 2. NOT run on a device.

## 4. R34a - "improve the prediction engine ... see if there are any models or other glide engines it can learn from or adopt ... Google gave me developer permission to reverse engineer gboard code"

### 4.1 Gboard: what was and was NOT done, and why (plain words)
* **No Gboard code, library or model was decompiled, read or copied.** Reasons, in order of weight: (1) this repository is PUBLIC and the hooks copy chat into it, so anything derived from Google's closed files would be published to the world; a permission given to the owner personally is not a licence to redistribute Google's weights or code, and the owner cannot hand such a licence on; (2) the permission cannot be checked from here and nothing in the sandbox holds a Gboard APK (it comes through the Play Store or a phone's system image; its glide decoder and models sit in closed native libraries); (3) what makes Gboard's glide typing good is already described by Google's own PUBLISHED papers and an open model of the same design is already inside Swoop (R30), so reverse engineering would add risk and little knowledge. The earlier verdict (R30 section 1) stands.
* What Google published (and what Swoop already has of it, from R20 / R29 / R30): a spatial model trained on huge amounts of real gestures (LSTM + CTC, Alsharif et al. ICASSP 2015, Ouyang et al. 2017) -> Swoop: the open FUTO-design network as a second opinion (`ShapeNet`, `ShapeRescorer`, +4 points on real swipes); the decoder as a finite-state search over keys with a word model composed in (Ouyang et al. 2017) -> Swoop: lexicon search with the word prior and the word before in the score; a neural next-word model trained by federated learning (Hard et al. 2018) -> Swoop: word pairs and the person's own words, no neural next-word model (R31 idea, not built); per-user touch offsets (`TouchField`, thumb habit); revising the word before once the next one is known (`revisePrevious`); learning from corrections. What Gboard has and Swoop cannot have: its training data, the compute to train a large model, and on-device federated learning.
* If the owner wants to go further with Gboard: do the reading on his own computer, never put a Google file, a decompiled listing or weights into this repository or the chat (they are copied into the repo), and tell me only findings in his own words (a number, a design idea). I will not build on files whose licence I cannot see.

### 4.2 Other glide engines (what each does; what is open)
| engine | licence / state | what it does that Swoop does not | verdict |
| :- | :- | :- | :- |
| AOSP LatinIME, HeliBoard, OpenBoard | Apache-2.0 / GPL-3 forks | their glide typing needs Google's closed `libjni_latinimegoogle.so` (R30 says so after reading their READMEs); the open part is the dictionary format (`.dict` with bigrams, probability + "not a word" flags) and the proximity-key correction for tapping | nothing to adopt for gliding; the bigram-heavy dictionary idea is the one thing: see 4.4 |
| FlorisBoard, AnySoftKeyboard | Apache-2.0 | statistical / template glide decoders in Kotlin / Java: prune words by first and last key, then compare the finger's path with each word's ideal path (SHARK2 style); no learned shape model | Swoop's decoder already does this and more (R20 section 3); not re-verified in this session, so no claim about their code |
| FUTO Keyboard, FUTO Swipe paper | models and data MIT (R30) | a neural encoder + decoder trained on ~900k real swipes, layout agnostic; top-1 92.9 % without a language model | adopted in alpha10 as the encoder half only (+4 points); the decoder half (304 K parameters) is NOT used: Swoop's lexicon search plays that role and takes the language model into the search |
| `youcoded/swipe-typing` (BiGRU + pointer, MIT, 529 K parameters), `giofolf/omniglide` (MIT) | open weights | a second, differently built learned shape model | an ensemble of two nets might add about a point but doubles the cost on the 32-bit tablet that is already the speed worry (a plain-Kotlin pass of the first net is 15-22 ms on a PC; the tablet has not been measured). NOT built; listed as the next option |
| SHARK2 (Kristensson & Zhai 2004) | paper | shape + location channels, a word-frequency integration; the baseline FUTO measured at 80 % top-1 | Swoop is above it |

### 4.3 Where the remaining errors are (measured before this session, R24 / R30 / R32, real FUTO swipes, phone-sized keys)
After the network re-ranker the first guess is right 92-94 % and the right word is in the first three 97 %: the remaining misses are look-alike words (same first and last letter), rare words and names, and short words read as long ones: i.e. the choice between words the PATH cannot separate. Only the LANGUAGE can separate them. Swoop's language side is the weak half: word counts from four sources (good) but word PAIRS from two small ones (SymSpell / Google Books 243 k pairs, Tatoeba sentences 143 k pairs after pruning) and no three-word table at all (the three-word phrases in `PersonalModel` are only the person's own).

### 4.4 Experiment 1: a much bigger word-pair model from web text (REAL swipes, measured, NOT adopted)
The one half of the engine that Google's papers say matters and that Swoop has least of is the language model: pairs came from two small sources and there is no three-word table. So the pairs were rebuilt from a big corpus and the whole decoder was measured on thousands of real swipes.
* Text: four shards of C4 (`allenai/c4`, English web text, ODC-BY; 1 425 269 documents, 491 million running words of the list's vocabulary), counted with the new `tools/glide/count_pairs_big.py` (numpy, 7 s per 36 000 documents; a stretch of plain words ends at punctuation, digits, line ends and words not in the list, as the keyboard has no word before it either). 2.03 million pairs with 5 or more sightings.
* Mixed into the shipped list the way R17 did the Tatoeba pairs (`mergePairs`, weight 0.85): candidate A = pairs seen 30+ times, at most 40 per word: 541 230 pairs (shipped list: 303 532), file 4.0 -> 5.4 MB; candidate B = 10+ times, at most 60: 972 712 pairs, 8.0 MB.
* Measured with `ShapeNetEvalTest` (the shipped decoder with the word before from the sentence, then the network hybrid, three disjoint real-swipe sets: slice A first 8 MB of FUTO dev, slice B 12 MB from byte 100 M, slice C the FUTO TEST split; run as `GLIDE_KLX=<list> REAL_SWIPES=1 java ... JUnitCore ...ShapeNetEvalTest`, about 3 minutes):

| list | slice A shipped / hybrid first choice | slice C | slice B |
| :- | :- | :- | :- |
| shipped (alpha12) | 87.9 / 92.3 | 90.6 / 94.4 | 88.8 / 92.3 |
| candidate A (541 k pairs) | 88.3 / 92.2 | 90.8 / 94.3 | 88.7 / 92.6 |
| candidate B (973 k pairs) | 88.3 / 92.2 | 90.9 / 94.3 | 89.1 / 92.8 |

  The decoder alone gains about +0.3 points; with the network's second look the gain is -0.1 / -0.1 / +0.5, i.e. nothing. On the everyday-sentence yardstick of the tap strip (`PredictionEval`, 1 250 words of casual text) the web-text pairs are WORSE than the shipped ones (register mismatch: web pages are not chat): next word in the strip's three places 28.7 % -> 27.3 % (A) / 27.2 % (B), right word on the strip after two letters 79.0 % -> 72.5 % / 73.5 %, keystrokes saved 51.7 % -> 49.5 % / 49.7 %. **Verdict: more word pairs do not move glide accuracy (the pair table is not the bottleneck), so the 1.4 to 4 MB would be dead weight on the tablet. Not adopted.** (It would still raise the next-word box; that was not measured here and the owner did not ask for it.) The counting script stays in the repository for the day a trigram table is tried.

### 4.5 Experiment 2: is the way the network and the language are added up the problem? (no)
The hybrid is `score + 0.7 * logP(network)`. `ShapeNetEvalTest` (R34_GRID=1) searched, on the same three real-swipe sets, a grid of: how much the language side counts (beta 0.8 to 2), how much the network counts (w 0.4 to 1.2), and the network's log P per letter or per sqrt(letters). The best cell (93.33 % first choice over all 5 400 swipes) is 0.13 points above the shipped cell (93.20) and the optimum is flat in every direction: **the shipped weights are already at the top; nothing to gain by re-weighting.**

### 4.6 Where the remaining misses are (R34_MISSES=n, hybrid, same three sets; words only)
First choice is right 92.3 / 94.4 / 92.3 % (A / C / B); the right word is in the first three 96 / 97.8 / 96.9 %. The misses:
* slice C (test split, 127 misses = 5.6 %): 39 look-alikes with the same first and last letter, 14 where a shorter word was chosen, 1 longer, only 4 where the right word is not among the 40 candidates. Nearly all are twins ONE KEY apart where both words are common: is/us, in/on, it/or, of/off, has/had, hit/hot, but/bit, our/or, son/soon, first/frost. 
* slice B: the same picture (42 look-alikes of 136); slice A: 45 of its 103 misses have the right word outside the candidates (a few donors with sloppy or off-set swipes; slices B and C have 4 each).
* In the twin cases the network often outvotes a sensible language preference (e.g. meant "is" after "he", network log-likelihood 5 nats in favour of "us"): a reading of the path, not a missing fact about English. Only a better reading of the finger can fix those: that is what per-person learning (touch plane, shape memory) is for, and what this phone-sized public data cannot show for the owner's tablet.
**Conclusion for R34a: on public real swipes the engine is at the top of what its inputs can give (92-94 % first, 97 % in the first three; the open FUTO network alone reports 93 % with no language model). The next step that can still move the owner's numbers is data from HIS tablet:** see section 5.

## 5. R34a2 - Glide practice: real glides from the owner's tablet (built; the owner's step is next)
Everything in sections 4.3-4.6 is phone-sized public data. The owner's tablet has bigger keys, another panel and another thumb, and "a lot is still wrong" there: nothing in the sandbox can say why, and guessing has failed three times (R27, R28, R33). So the keyboard now collects the one thing that can settle it, with nothing private in it:
* **Settings > Help > Glide practice** (`PracticeActivity`): 40 everyday words are shown one at a time (`GlidePractice.WORDS`: the, and, for, or, there, is, in, it, of, to, ... plus his look-alike pairs our / out, make, access). He glides each with Swoop in a box whose private option `app.swoop.practice=1` makes the keyboard hand over that glide (`Practice.sink`, `KeyboardPresenter.onGlideEnd`): the path of the finger (view pixels, ms), the words the keyboard offered, the key positions and the view size it decoded on. A box with the option learns nothing (no personalised learning flag). The sink exists only while the screen is open and only that box is ever handed over, so nothing typed anywhere else is kept (tests: `KeyboardPresenterTest` 2).
* The screen ends with "first word right N of 40" and the missed words (asked for -> typed), and "Save the file": one `Swoop glide practice <date>.txt` in Downloads (no picker, no permission). The file starts with the magic line `SWOOP-GLIDE-PRACTICE 1`; `tools/secretscan.sh` refuses to commit it and `capture_inbox.sh` replaces a pasted copy by a note (self-test in `tools/test_handoff.sh`). It is ATTACHED to the chat, never pasted.
* What I do with it next session (`PracticeEval`, test-side, `PRACTICE_FILE=<abs path>`, run with `java ... JUnitCore app.kestrel.core.input.glide.PracticeEval`; `build/r30/swipe_encoder.bin` = the asset, for the network): re-decode every glide on the RECORDED key positions with the shipped decoder, alone and with the network; list the misses with the rank of the right word; compare with what the keyboard answered when they were made; sweep `shapeW`, `visitCap` and `lmMin`, the values that `GlideParams.forPitchDp` only guesses for big keys (R24 section 4: "THE TABLET SIDE HAS NO REAL-SWIPE EVIDENCE"). `PracticeEvalTest` proves the chain on simulated tablet glides. If a tablet value wins clearly on his 40 glides it is changed (and re-checked on the phone-sized real swipes so they do not move).
* Honest limits: 40 glides give a rough number (one standard error is about 4 points), enough to tell "92 %" from "70 %", not to tune a tenth of a point; paths of a person who knows he is being measured are tidier than everyday ones. Not run on any device.
