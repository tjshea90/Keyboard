## 1. R34d - "make the delay from first key to glide instant so it doesn't erroneously type one letter" (done, tests red -> green)

History: R28b (alpha8) cut the glide start from 5 dp to 2.5 dp and fixed the padding and the second-thumb hand-over. The owner reported the stray letter again, so the threshold was not the cause. Reading every place where a letter can be typed while a finger is down on a letter key
(`KeysView.pressDown / pressMove / pressUp / ACTION_POINTER_DOWN`) found three paths that type the FIRST key's letter although a glide is meant. All three sit in the window between "finger down" and "finger has moved 2.5 dp" (the owner's "delay from first key to glide"):

| # | what happened | why | fix (all in `KeysView`) | test (RED on alpha12, green now) |
| :- | :- | :- | :- | :- |
| 1 | A quick flick whose only touch events were DOWN and UP (a panel that sends no MOVE in between, or a flick faster than one sample) typed the letter the finger went down on, although the lift point was far away. | `pressUp` decided "tap" for any touch that was not yet `gliding`, without looking at where the finger lifted. | at the lift: a touch that has moved more than the glide start distance is a glide (`armed && movedFar(x, y)`), then the usual tap-or-glide decision at the end of the stroke. | `aFlickWhoseOnlyEventsAreTheTouchDownAndTheLiftIsAGlideNotTheFirstLetter` |
| 2 | A second finger that touched the screen in that window (a thumb that holds the tablet, a palm, a ghost touch of a cheap panel, the other thumb of two-thumb typing) TYPED the first finger's letter at once and switched tracking to itself, so the glide the first finger was about to draw was lost and a stray letter stayed. | `ACTION_POINTER_DOWN` while `armed` but not yet `gliding` called `finishHeldLetter()`. | The new finger is only recorded while the first finger may still glide (as R28b already did once a glide was running). The first finger carries on. If the NEW finger moves first it is the glide and the first one was a tap (typed then). If the first finger lifts without moving it is a tap and the recorded finger carries on as a new touch. A quick tap of the new finger that lifts first is typed after the first finger's letter (press order kept) and dropped when the first finger glides. | `aSecondFingerThatTouchesTheScreenJustBeforeAGlideStartsDoesNotCostTheGlide` and four order tests (`twoThumbsThatOverlap...`, `aSecondThumbThatTapsAndLiftsFirst...`, `aSecondThumbThatMovesWhileTheFirstOnlyJustLanded...`) that already passed and must stay green |
| 3 | A thumb that RESTS on a letter key (it holds the tablet; the 7-inch tablet is held by its edge) types that letter when another finger lands or when it lifts. | same path as 2; and a resting thumb's tremor over 2.5 dp counted as a "glide" that stayed on its key and typed its letter at the lift. | A finger that has stayed on a letter for 300 ms (`RESTING_MS`) without leaving its key when another finger lands is a holding thumb: it is let go without typing anything, the new finger is the one that types or glides. A fast two-thumb overlap is far under 300 ms. | `aThumbThatHoldsTheTabletOnALetterTypesNothingWhenTheOtherFingerGlides`, `aThumbThatHoldsTheTabletAndAnotherThatTapsTypeOnlyTheTap` |

Not changed on purpose: the 2.5 dp start (tremor over it still ends as a tap at the lift: `stayedOnKey`), the strip/padding rules, rollover typing with glide off (a second finger still types the first letter at once there).
Honest limit: nothing here shows which of the three the owner's tablet hits; each is a real path found by reading the code and reproduced by a test. `Diagnostics` counts how often a resting finger was let go (the existing "a resting second finger was ignored N times" line), so the next report says if path 3 happens.
